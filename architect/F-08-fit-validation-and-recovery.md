## Pipeline (`Parse`)

```
1  acquire a parse slot (select on slots and ctx.Done()); ctx done → canceled
   t0 := now (slot wait excluded); defer release; defer recover → internal; defer log line
2  len(data) > MaxBytes                              → limit (bytes)
3  !looksLikeFIT(data)                               → not_fit
4  dctx := WithCancelCause(ctx) + WithTimeoutCause(Timeout, errTimeLimit)
   l := listener with budgets and cancel
   integ := walk(dctx, data, l)                      (section Sequence walk)
5  if the walk stopped on a context cause:
      parent ctx ended                               → canceled
      errTimeLimit                                   → limit (time)
      budget cause                                   → limit (<name>)
      errUnsupportedType                             → unsupported_type
6  no record with a valid timestamp                  → no_data
7  n := workout.SampleCount(rec); n == 0             → no_data
                                  n > MaxSamples     → limit (samples)
8  rec.Integrity = integ; w := workout.Normalise(rec); return w
```

`looksLikeFIT(b)`: `len(b) >= 12`, `b[0]` is 12 or 14, `len(b) >= int(b[0])`, `string(b[8:12]) == ".FIT"`. The data size and the header CRC are not part of the check: a header with data size 0 is a FIT file (R-c), and a wrong header CRC is a recovery (R-b).

The file type is checked in the listener (section Listener), so a course or monitoring file stops decoding right after its `file_id` and never reaches step 6.

## Sequence walk and recovery rules

The decoder is called **once per FIT sequence** on a fresh decoder (or one reset with `Reset`) over the bytes from the sequence start. `ingest` computes sequence boundaries from the header itself: `Size` (byte 0) and `DataSize` (bytes 4–7, little-endian). Messages end at `start + Size + DataSize`; the file CRC follows in 2 bytes.

```
pos := 0
loop:
  if integ.Sequences == MaxSequences → cancel(limit sequences); stop
  h := header at data[pos:]; integ.Sequences++; l.beginSequence(integ.Sequences)
  avail := len(data) - pos - h.Size
  patched := h.DataSize == 0                                   (R-c)
  res := decodeSequence(pos, h, patched, checksum: !patched)
  if res.err is CRC mismatch:                                  (R-b)
      integ.CRCFailed = true
      if l.seqMessages == 0 && !patched: res = decodeSequence(..., checksum: false)
      else: res.err = nil                                      (file CRC: messages are complete)
  switch:
    context cause                → stop (Pipeline step 5 classifies)
    patched                      → integ.Truncated = true; stop          (R-c)
    res.err == nil               → pos += h.Size + h.DataSize + 2
    EOF-type error and avail >= h.DataSize
                                 → integ.CRCFailed = true; stop          (only the CRC is missing, R-b)
    any other error              → integ.Truncated = true; stop          (R-a)
  if pos >= len(data) → stop
  if !looksLikeFIT(data[pos:]) → integ.IgnoredBytes = len(data) - pos; stop   (R-e)
```

"EOF-type" means `errors.Is(err, io.EOF) || errors.Is(err, io.ErrUnexpectedEOF)`. For a patched sequence, the decoder reads `io.MultiReader(patchedHeader, data[pos+h.Size:])`. `patchedHeader` is a copy of the `h.Size` header bytes with the data size set to `avail` and, for a 14-byte header, the header CRC set to 0. The library treats a header CRC of 0 as "not computed".

| Rule | Situation | Result |
| --- | --- | --- |
| R-a Truncation | A sequence stops before the end of its messages: EOF (file cut off, data size larger than the bytes present) or any decode error (missing message definition, invalid base type, …) | Every message delivered before the break is kept. A message is only delivered once all its fields were read (`decodeMessageData`), so a cut-off record never reaches the listener. `Truncated = true`; later bytes are not read. Accepted if a record survives (UP-3), else `no_data` |
| R-b CRC | File CRC wrong: the decoder reports it after the last message, when the listener already has every message. Header CRC wrong: reported before any message; the sequence is decoded once more with `WithIgnoreChecksum()`. CRC bytes missing (file ends exactly after the messages): treated as a failed CRC | `CRCFailed = true`, data complete, **no** UP-3 notice (OQ-33). Accepted (UP-2: "fails its CRC check … accepted") |
| R-c Unclosed file | Header data size 0: many devices write the real size only when they close the file | Decoded to the end of the bytes with checksum off; always `Truncated = true`. If such a file was in fact complete, the notice names the last record's time and nothing is missing; accepted (rare, harmless) |
| R-d Chained file | Another FIT header follows a complete sequence | Decoded into the same `Recording`. A later sequence whose `file_id.type` is valid and not `activity` is skipped (`SkippedSequences++`). A sequence without `file_id` counts as a continuation and is used |
| R-e Trailing bytes | Bytes after a complete sequence that are not a FIT header (padding, garbage) | Ignored, `IgnoredBytes` = their count; no notice |

After a truncation or a stop for missing CRC, no further sequence is looked for: without a trustworthy boundary, the next header cannot be found reliably.

**Decoder options (ADR-003 rev. 2).** Always `WithMesgListener(l)`, `WithBroadcastOnly()`, `WithNoComponentExpansion()`. Added only for a retry or a patched header: `WithIgnoreChecksum()`. Nothing else: no `WithLogWriter`, no `Next()`, no `CheckIntegrity()`. (v1.7, ADR-003 rev. 5, built in F-09 round 4) Each decoder call also gets a fresh record counter `c`: `WithMesgListener(l, c)` and `WithMesgDefListener(c)`. The walk stores the count of a sequence's last call as `seqSpan.records`, for the UP-9 strip (ADR-023 rev. 4 item 2). The counter changes nothing the listener sees, and nothing in `Integrity`, the report or any golden.

## Model changes (`workout`)

```go
// Integrity says how completely the file could be read (F-08; UP-2, UP-3).
type Integrity struct {
    Truncated        bool  // the file broke off; data after DataEnd is missing (UP-3 notice)
    DataEnd          int32 // time offset of the last intact record (s); set by Normalise, only if Truncated
    CRCFailed        bool  // a CRC check failed or the CRC was missing; the data was used as read
    Sequences        int   // FIT sequences found (> 1: chained file)
    SkippedSequences int   // later sequences of another file type, ignored
    IgnoredBytes     int   // trailing bytes that were not a FIT sequence
}
```

- `Recording.Integrity` is set by `ingest`; `Normalise` copies it into `Workout.Integrity` and, if `Truncated` and there are samples, sets `DataEnd = Samples.Offset[last]`. The streams end there, so the last sample is the last intact record. F-19 formats `DataEnd` as hh:mm:ss elapsed since the start (decision 11).
- `SampleCount(rec Recording) int` returns exactly `len(Normalise(rec).Samples.Offset)` without building samples: valid record times as offsets (`offsetOf`, R-1), sorted, equal seconds merged (R-2), plus `d − 1` for every step `2 ≤ d ≤ 4` (R-3). Memory: one `int32` or `int64` per record. It may share helpers with `buildTimeAxis` and `fillGaps`; a test pins the equality.
- `Derived` gains `ElevationLoss` and the record totals of R-11. Existing fields are unchanged.

**v1.1 additions to `Recording`** (filled by `ingest`, plain values, read only by `Normalise`; `Workout`, the report and the data file do not change):

```go
type Recording struct {
    // … as before …
    Sports         []RawSport // sport messages that a record followed, arrival order (D-12)
    SequenceStarts []int      // index into Records of the first record of sequence 2, 3, … (R-12)
}
type RawSport struct { At time.Time; Sport string } // At = time of the next record in the same sequence
type RawLap   struct { Sport string; Start, End time.Time; Totals Totals } // + Sport (lap.sport)
```

`Normalise` must not modify its argument (it receives slices that share memory with the caller); R-12 works on its own copy of the records, which `buildTimeAxis` already makes.

### R-8 addition: elevation loss

The same zig-zag pass also sums the confirmed drops (`ref − cand` when a downward run is confirmed, and at the end if `dir == −1`), with the same `H` and smoothing. `nil` under the same condition as the gain. Symmetry test: the mirrored profile gives loss = gain.

### R-11 Record totals (new, before R-10)

### R-12 Distance across sequences (v1.1, new; applied to the records before R-2)

**Problem (QA-08-r1-3).** Each sequence of a chained file is a complete activity file, so its `record.distance` starts again near 0. Joined as recorded, the stream folds back at every boundary: `Derived.Distance` is the last sequence's distance only, `AvgSpeed` is wrong (shown for a same-sport file), and the distance axis (AP-5), range distance (AP-7) and km splits (AP-8) would fold.

**Rule.** `SequenceStarts` splits `Records` (arrival order) into ranges, one per sequence. Walk them in order; `prev` is the last valid distance so far, after adjustment, and starts as "none":

```
for each range j in order:
    first := first valid distance in range j (arrival order)
    base  := 0
    if prev exists and first exists and first < prev / 2: base = prev      (v1.2, midpoint rule)
    every valid distance in range j += base
    if range j has a valid distance: prev = its last valid distance (arrival order) + base
```

| Case | Result |
| --- | --- |
| Later sequence restarts (`first < prev / 2`) | Offset by `prev`: the stream continues where the previous sequence ended |
| Later sequence continues the count (`first ≥ prev / 2`), including a small drop at the boundary (QA-08-r2-1: 2,994.99 after 2,995) | Unchanged by R-12; the small drop is then held by R-14 (v1.4) |
| `prev` is 0 (the previous sequences never moved) | Unchanged; an offset of 0 would change nothing anyway |
| A sequence without distance | Unchanged; `prev` stays, so the next sequence is compared with the last one that had distance |
| Decrease inside one sequence | Unchanged by R-12 (device data, F-02 R-6a); held by R-14 (v1.4) |
| One-sequence file (`SequenceStarts` empty) | Unchanged. Every existing golden except `chained-ride-run` is unaffected |
| No device distance (R-6b) | Nothing to do: the computed distance runs over the joined samples and is cumulative. Between two sequences it adds the straight line from the last fix to the next, as for a GPS dropout (AP-3) |

Only distance is cumulative among the fields we read. Laps, sessions and timer events carry absolute times; session and lap totals are per span. Sequences are assumed to be in time order in the file. If a later sequence lies earlier in time, R-2 sorts its records first and the stream can still fold. That is accepted: no known writer does it. `SampleCount` is unaffected. (v1.4) R-14 then holds such a fold flat, so the stream never falls; the lost distance shows as a flat stretch, not as a fold.

**Restart test (v1.2, QA-08-r2-1 and QA r2 Q2).** A later sequence's first distance is either near 0 (the writer restarted its count, the expected case for a sequence that is a complete activity file) or near `prev` (the writer carried its count on). The midpoint `prev / 2` assigns it to whichever it is closer to. It needs no tolerance constant and absorbs any boundary smoothing.

| Rule considered | Verdict | Why |
| --- | --- | --- |
| v1.1 `first < prev` | Replaced | A count carried on, but written 1 cm lower at the boundary, is offset by the whole previous distance (QA probe: 8,985 m instead of 5,990 m, summary 7.49 m/s instead of 5.0) |
| Always offset every later sequence (Q2) | Rejected | Whether any writer carries the count across sequences is **not known**: no real chained activity file is available (QA r2, "Not run"). If one does, every such file would have its distance inflated by the whole previous distance. The midpoint rule is correct for both kinds of writer |
| Absolute threshold ("first below x m") | Rejected | A restart whose first record comes after some movement (GPS lock, auto-start) can exceed any fixed x |
| **Midpoint `first < prev / 2`** | **Chosen** | Wrong only if a restarting sequence's first recorded distance is at least half the previous sequence's whole distance, i.e. after a very short previous sequence. The distance then misses `prev`, which is at most twice that first value, and the stream shows one drop. A carried-on count is never misread unless it falls by more than half, which is not smoothing |

Trigger to revisit: a real chained activity file in the corpus whose boundary the midpoint rule gets wrong.

### Sport timeline (v1.1; replaces the membership sentence of F-02 R-5)

**Problem (QA-08-r1-1).** A truncated file usually has no `session`, so samples had no sport: running cadence was not doubled, the workout sport was `""`, and R-7 used the default threshold. In a truncated triathlon the run tail fell back to the T2 transition session.

**Sport hints.** Built once per `Normalise`:

- each `RawSport`, at offset `offsetOf(StartTime, At)` (R-1);
- each `RawLap` with a sport, at the lap's start offset.

Hints with sport `""`, `multisport` or `all` (FIT profile names) are dropped: they do not name the sport of a leg. Hints are sorted stably by offset. On equal offsets a `sport` message ranks after a lap (so it wins); among hints of one kind the later in arrival order wins.

**`sportAt(t)`**, the first rule that applies:

| # | Rule |
| --- | --- |
| 1 | A session with `Start ≤ t ≤ End`: the first such session in file order (F-02 R-5, unchanged) |
| 2 | The winning hint with `Eprev(t) ≤ offset ≤ t` (latest offset). `Eprev(t)` = the largest `End` of a session with `End < t`; −∞ if there is none |
| 3 | The session with the latest `Start` earlier than `t`; on equal starts the first in file order (F-02 E-5, unchanged) |
| 4 | The first session in file order |
| 5 | No session at all: the hint with the earliest offset; no hint: `""` |

Why this order: a session is the device's own statement for the span it covers, so it always wins. A hint is used only for samples no session covers, and only if it was written after the last session that ended before the sample. A `sport` message at the start of a multisport file therefore never overrides a later leg, and in a truncated triathlon the run's own hint names the run tail instead of the T2 session.

Why both sources (QA Q3):
- The `sport` message is written before the first record by every local real file (4 files, 2 manufacturers). It covers the commonest UP-3 case, a watch that died mid-run.
- `lap.sport` (3 of 4 real files) exists only once a lap has ended. It is a second source for legs of a multisport file.
- Whether multisport devices write a `sport` message per leg is not known (no real multisport file was available). The order above is correct either way. (v1.3) A local real triathlon file now exists; the operator reports the answer for its writer (section R-13, Real-file check, point 4), into the QA report.

**Uses.**
- R-5: a sample's cadence is doubled if `sportAt(Offset[i])` is `running`, `walking` or `hiking`; a lap's averages and maxima if `sportAt(lap.Start)` is; a session's by its own sport (unchanged).
- R-7: the moving threshold of sample `i` is that of `sportAt(Offset[i])`.
- R-9 and R-10 through the workout sports `S` (next section).
- (v1.3) R-13: `inTransition(t)` is true only when **rule 1** gives a session with sport `transition` (D-23). It reuses the precomputed `cover` step function; same complexity.

**Complexity (QA-08-r1-5, ADR-017 rev. 1).** No loop over sessions, laps or hints per sample (today `sessionAt` scans every session for every sample, `cadence.go:10`). One way that meets the bound: rules 1, 3 and 4 change their answer only at session starts and at `End + 1`. Evaluate them once per such breakpoint (at most 2 × 100 points, each O(sessions)) into a step function. Then walk the sorted sample offsets with one pointer into the step function, one into the sorted hints and one into the sorted session ends (for `Eprev`). That is O(n + k log k). A test pins equality with a direct reference implementation of the table (section Tests).

### Workout sports `S` and R-9 sport (v1.1; replaces the sport bullet of F-02 R-9)

`S` = the distinct values among the `Sport` of every session, plus `sportAt(Offset[i])` for every sample `i` of the record leg (section Summary, step 0), if there is one.

| `S` | `Workout.Sport` |
| --- | --- |
| empty (no session, no record leg) | `""` |
| one value | that value (may be `""`) |
| two or more | `multisport` |

The same `S` decides **mixed sports** in R-10 (`|S| ≥ 2`), so the summary hides average speed and cadence exactly when the sport is `multisport`.

| File | Sport |
| --- | --- |
| Triathlon, brick, chained ride + run | `multisport` (unchanged) |
| Ride split into two cycling sequences (`chained-ride-ride`) | `cycling` (v1.0: `multisport`) |
| Run cut off before its session (`run-30min-cut-60`) | `running` (v1.0: `""`) |
| Cut file whose writer wrote no `sport` message and no lap ended with a sport (`ride-30min-cut-60`) | `""` (unchanged: no source exists) |

**Q2 / OQ-36 (confirmed by the user, 15 Oct 2026).** A ride split in two is not a multisport workout, and OQ-22 needs its real sport to choose pace or speed and the cadence unit. The user confirmed the rule as built; AP-12 now says "the sport is 'Multisport' when the sessions have more than one sport, otherwise that sport" (requirements, in parallel). Nothing changes in code.

### R-13 Transition legs (v1.3, OQ-38; between R-3 and R-4)

**Problem.** Multisport devices record a transition (T1, T2) as a session with sport `transition` and keep writing records in it: position, distance, heart rate, and often speed and cadence (a local real triathlon file does). The user, 15 Oct 2026: "Let's keep the transitions simple. I want gps, heart rate and elevation. Since transitions almost always include changing parts of your outfit there is no meaningful definition of speed and such." AP-4 now says so. Until v1.2, transition speed and cadence were charted and could win the workout's maxima.

**Transition session, sample, lap (D-23, user answer 9: "a transition is only a session with FIT sport 'transition'").**
- A **transition session** is a session whose own `Sport` is `transition`. No other session is one, whatever its sub-sport, name or speed; every other session keeps all its data.
- A **transition sample** is a sample `i` with `inTransition(Offset[i])`: rule 1 of the sport timeline (the first session in file order with `Start ≤ t ≤ End`) is a transition session. A sport hint (rule 2) or a fallback (rules 3 to 5) never makes a transition sample.
- A **transition lap** is a lap with `inTransition(lap.Start)` (as R-5 places a lap by its start).

**Allow-list (D-21; user answers 1, 3, 7).** At transition samples and in the totals of transition sessions and laps, only these survive. Everything else is dropped: a sample value becomes `NaN` (a missing sample), a total becomes `nil` (not recorded).

| Kind | Kept | Dropped |
| --- | --- | --- |
| Streams | `Lat`, `Lon` (the user's "gps"), `Altitude` ("elevation"), `HeartRate`, `Distance` (answer 1), `Temperature` (answer 3) | `Speed` (and with it pace in the browser), `Cadence`, `Power`; **any stream added to `Samples` later**, unless it is added to this list |
| Totals of a transition session or lap | `ElapsedTime`, `TimerTime`, `Calories`, `Distance`, `Ascent`, `Descent`, `AvgHeartRate`, `MaxHeartRate`, `AvgTemperature`, `MaxTemperature` | `AvgSpeed`, `MaxSpeed`, `AvgCadence`, `MaxCadence`, `AvgPower`, `MaxPower` (answer 4: "including the device's own transition session totals") |

The list is one table in `transition.go`, keyed by stream and by `Totals` field. A test fails if a stream of `Samples` or a field of `Totals` is in neither column, so a new stream or total needs an explicit decision. Time totals and calories describe the leg, not a pace; they stay.

**Order in `Normalise` (D-22).**

```
R-1                 sessions, laps, timer events (unchanged)
R-12, R-2, R-3      buildTimeAxis(continueDistance(…)), fillGaps (unchanged)
R-14 (v1.4)         the device distance stream never falls (section R-14)
                    tl := newSportTimeline(sessions, hints)      moved up: it needs no samples
R-13                maskTransitions(&w, tl): samples, transition sessions, transition laps
R-4                 settlePresence
R-5 to R-11, R-9, R-10   as before, with the same tl
```

- After R-3: a sample filled inside a transition is masked like a recorded one.
- Before R-4: a stream whose only valid values were in transitions becomes absent, so no empty chart is drawn.
- Before R-5 to R-11 and R-10: every derived value, the record leg and the summary fallbacks read the masked values. The server's numbers then agree with what the browser can compute from the data file (the R-11 rationale), and no transition value can win a maximum.

Complexity: one timeline lookup per sample (O(n log k)), as R-5 already does; within D-16.

### R-14 The distance stream never falls (v1.4, QA-08-r3-2; right after R-3)

**Problem.** F-02 R-6a kept the device's distance stream as recorded. QA r3 probed the local real triathlon file (QA-08-r3-2; the counts are in the QA report only): the distance falls at the T1 to bike boundary, drops to near 0 in several runs inside the open-water swim after it has already advanced, and falls once more at a lap start in the bike leg. The summary is not affected: its distance comes from the sessions. But every consumer of the stream treats distance as a running count:

| Consumer | Effect of a fall |
| --- | --- |
| Readout (F-05, built) | Shows about 0 m in the middle of the swim |
| Distance axis (AP-5, F-17) | The chart folds back over itself |
| Range distance (AP-7, F-17; TD: prefix lookups `d[end] − d[start]`) | Zero or negative for a range that ends in a fall |
| Km splits (AP-8, F-18) | The same kilometre is crossed twice |
| Gradient colouring (AP-9, F-25) | Δaltitude ÷ Δdistance with a negative or huge Δdistance |
| `Derived.Distance`, R-11 `AvgSpeed`, the record leg (server) | Read the last value, which may lie below an earlier one |

**Decision (D-25).** This is writer data that the server normalises, not data that the browser must tolerate. After R-3, each valid value of the **device** distance stream becomes the largest valid distance up to and including it:

```
high := none
for i in time order (Samples, after R-12, R-2, R-3):
    if Distance[i] is NaN: continue            missing stays missing; high is kept
    if high exists and Distance[i] < high: Distance[i] = high
    else: high = Distance[i]
```

O(n), in place on the workout's own stream (the copy `buildTimeAxis` made); the caller's `Recording` is unchanged. It runs before R-13, R-4 and R-6b.

**Order against R-3 (v1.5, QA-08-r4-1): hold after `fillGaps`.** R-3 first interpolates each filled sample between its two **recorded** neighbours, then R-14 holds the whole stream, filled samples included. So a filled value is never computed from a held value. Example (records at 0 s, 1 s and 5 s with distances 100, 50 and 200; the 4 s gap is filled at 2, 3, 4 s): R-3 gives `[100 50 87.5 125 162.5 200]`, then R-14 gives **`[100 100 100 125 162.5 200]`**. Holding first would give `[100 100 125 150 175 200]`, which is wrong. R-6b's computed distance is non-decreasing by construction and is built later, so R-14 only ever sees device distance.

| Case | Result |
| --- | --- |
| Non-decreasing stream (every synthetic file; R-12 output of a restarted sequence) | Unchanged, bit for bit |
| Small drop at a sequence boundary or from smoothing (QA-08-r2-1 shape: 2,994.99 after 2,995) | Held at the higher value until the count passes it; no step is negative |
| Run of near-zero values, then recovery (the real swim) | Each run shows the last high value; the stream continues when the device's count does |
| Downward correction (the real T1 to bike fall) | Flat until the device's count passes the previous high; on the distance axis that stretch has no width |
| Sequence in the wrong time order, which R-12 accepts (section R-12) | A flat stretch instead of a fold |
| Missing samples | Stay missing; they neither reset nor advance `high` |
| No device distance (R-6b) | Nothing to do |

**Effects on later rules.**
- `Derived.Distance` (last valid value) becomes the largest valid device distance. It changes only where the device's last value lies below an earlier one.
- R-7, speed from `Δdistance / Δt` (only without a speed stream): a held step has `Δd = 0`, so it is not moving, as the fall was before. The jump back up after a dropout no longer counts as one fast step.
- R-11 `AvgSpeed` follows `Derived.Distance`. The record leg's `Distance` is at least 0 by construction; its clamp stays as a guard.
- Summary: device totals are untouched. Only step-2 fallbacks and record legs read the stream.
- Data file (F-03): format unchanged. The distance column never decreases.

**Options considered.**

| Option | Verdict | Why |
| --- | --- | --- |
| Tolerate in the browser: widen the F-17/F-18 hand-off only | Rejected | The readout (built), the distance axis, ranges, splits and gradient would each need their own rule, and the server's `Derived` and record leg would disagree with the page. The same reasoning put R-13 on the server. The TD (Code structure) puts every distance rule in `workout` |
| **Running maximum on the server** | **Chosen** | One rule in one place; no threshold and no knowledge of the writer; right for dropouts, smoothing drops and corrections alike |
| Turn a fall into missing samples | Rejected | Needs a threshold to tell a dropout from a correction. It leaves holes in the readout and the splits, and the distance axis gets the same shape as with the running maximum |
| Continue per session, like R-12 at session starts in one sequence | Not now | The real file's count runs on through the boundary and is corrected down, not restarted: the stream's last value matches the sum of the sessions (QA: `derived.distance` ÷ `summary.distance` rounds to 1.00). An offset would add the whole previous distance again. No known writer restarts distance per session inside one sequence; trigger below |
| Rebuild distance from positions where the device's falls | Rejected | Swim GPS is the least reliable source, and a mixed stream would disagree with the device's session totals |

**Costs.**
- Time spent in a held stretch has no width on the distance axis, and a range inside it has distance 0 while time passes. That is the nature of a distance axis (a standstill looks the same); the time axis is unaffected.
- An upward spike (one value far too high) would be held for the rest of the workout: everything after it is flat until the device passes it, and `Derived.Distance` becomes the spike. No file shows this.
- A writer that restarts distance at every session inside one sequence would get later legs flat until they pass the earlier total. No file shows this; the real-file check (b) below detects it.

**Triggers to revisit.** A real file with an upward distance spike; a real file whose distance restarts at a session start inside one sequence (check (b) fails). The second would extend R-12's midpoint rule to session starts.

**Reversible.** Data files are regenerated from the originals on every deploy (ADR-005); a change to R-14 is a code change plus the next deploy.

**Real-file check (v1.4; replaces point 3 of section R-13, Real-file check).** Local only, reported by manufacturer only, numbers only in the QA report: (a) the `TestCorpus` distance invariant (section Tests) passes on every local real file; (b) for every complete real file with sessions and a device distance stream, `derived.distance ÷ summary.distance` still rounds to 1.00; a file where it does not is reported; (c) no real golden changed outside the keys allowed for R-14 (the distance stream and the values derived from it; the list is in history, "Changes for the backend engineer (v1.4)").

### Summary (R-10, revised; replaces F-02 R-10; v1.1: combined over legs)

**Step 0, legs (v1.1, QA-08-r1-2).** The summary combines legs, not sessions:

- Every session is a leg, with its device totals (after R-5) and its `Sport`.
- **Record leg.** It exists if (`Integrity.Truncated` **or** there is no session) **and** at least one sample has an offset greater than `Elast`, the largest session `End`; with no session, every sample qualifies. Its samples are `i0 … n−1`, from the first sample with `Offset > Elast`. It stands for the part of the workout that no surviving session describes: the cut leg of a truncated file, or the whole of a file written without sessions. Its values come from the records:

| Field | Record leg value |
| --- | --- |
| `ElapsedTime` | `Offset[n−1] − legStart`; `legStart` = 0 without sessions, else `Offset[i0]`. (v1.3) Never read by the summary: R-10.E takes the wall time whenever a record leg exists |
| `Distance` | `lastValid(Distance[i0:]) − ref`, at least 0. `ref` = the last valid distance before `i0`, else 0. `nil` if the leg has no valid distance. The stream is continuous across sequences by R-12 |
| `Ascent`, `Descent` | R-8 (same smoothing and `H`) over `Offset[i0:]`, `Altitude[i0:]`; `nil` as in R-8 |
| `MaxSpeed`, `MaxHeartRate`, `MaxCadence`, `MaxPower`, `MaxTemperature` | Maximum of the stream over `i0 … n−1`; `nil` if it has no valid value there |
| `TimerTime`, `Calories`, every average | `nil` |

Why only when truncated or session-less: in a complete file, the device's sessions are its statement (AP-2). A record one second after the session end must not turn a one-session file into two legs and drop its device averages.

**Complete later sequence without a session (v1.2, D-20, QA r2 Q1): accepted, no record leg.** In a complete chained file whose later sequence has records but no session, the summary's distance, ascent, descent and maxima come from the sessions only (QA probe: 2,995 m of 5,990 m). The elapsed time is the wall time over both sequences (v1.3: R-10.E's single-recording exception does not apply, because the records come from two FIT sequences; v1.2 said so but its R-10.E only covered 2+ legs, engineer probe: summary 9, derived 109), and the streams, charts and `Derived` hold everything. Reasons: Garmin's FIT activity-file definition lists `session` among the required messages, so a complete sequence without one is malformed. No writer is known to produce it. Detecting it needs a sequence number on every session, which no other rule needs. Trigger to revisit: a real file of this shape. The extension would then be "a record leg also covers the samples after the last session `End` when they come from a later sequence without a session".

**R-10.E `ElapsedTime`: wall time unless one session is the whole recording (v1.2, D-18; OQ-35 answered by the user, 15 Oct 2026; v1.3 restated as one rule).**

```
singleRecording := len(Sessions) == 1  &&  no record leg  &&  recordSequences(rec) <= 1
Summary.ElapsedTime =
    the session's device ElapsedTime        if singleRecording and the device recorded it
    Derived.ElapsedTime                     otherwise (copy of the value; nil without samples)
```

`recordSequences(rec)` = the number of FIT sequences that delivered at least one record with a valid time: the ranges of `Records` split at `SequenceStarts` (as in R-12) that hold such a record. A skipped or empty sequence (repeated start) counts 0. O(n), in `sequences.go`.

`Derived.ElapsedTime` = `Offset[n−1]`, the time from the workout start (t = 0, F-02 R-1) to the last record. Transitions, pauses and the gaps between sessions or FIT sequences are included. The legs' own `ElapsedTime` values are never added up. User: "I swam for 1 hour then rode a bike for 1 hour, what elapsed time should be shown when hovering over the 30 minute mark of the ride? 90 minutes, elapsed time should be tracked across the entire workout".

- **Why the device value survives only there:** a session's device elapsed time describes its own recording. When it is the whole workout and the whole recording, it is the device's statement (AP-2, OQ-22) and differs from the wall time only by the device's rounding or records just outside the session; that is accepted. Any other shape has no single device statement for the whole workout, so the summary uses the time axis.
- **Invariant:** apart from the single-recording case, `Summary.ElapsedTime` equals the cursor's elapsed time at the last record (section Time axis across legs).
- **Why `Derived.ElapsedTime` and not "last record − first record":** it is exactly what the cursor shows at the last sample. The two differ only when a session or lap starts before the first record, because t = 0 is then that start (R-1). AP-2 now says "from the workout start to the last record" (OQ-37, resolved).
- **No samples** (only reachable by calling `Normalise` directly; `Parse` rejects it as `no_data`): one session → its device value, as in v1.2 (`recordSequences` is 0); otherwise `nil`.
- **Why not "a session that covers every sample" instead of counting sequences:** a record one second after the session end, common in complete files, would switch one-session files to the wall time and change device values by rounding. The sequence count is exact and changes no golden.

The second half of the user's OQ-35 answer already holds: elapsed time at the cursor counts from the workout start across every leg. Nothing is changed. This section states it so that no later feature breaks it.

## Limits

Mechanism, defaults and rationale: ADR-017. Summary for the engineer:

| Limit | Default | Enforced at |
| --- | --- | --- |
| `MaxBytes` | 20 MiB | Pipeline step 2, before any decoding |
| `Timeout` | 10 s | Decode deadline (per message, per sequence) |
| `MaxRecords`, `MaxLaps`, `MaxSessions`, `MaxTimerEvents`, `MaxFieldDescriptions` | 500,000 / 10,000 / 100 / 100,000 / 256 | Listener, on arrival |
| `MaxSequences` | 64 | Sequence walk |
| `MaxSportMessages` (v1.1) | 1,000 | Listener, on arrival; limit name `sport_messages` (ADR-018 rev. 1) |
| `MaxSamples` | 500,000 | `SampleCount` before `Normalise` |
| `MaxConcurrent` | 2 | Parse slots |

**Measurement and stop rule** (ADR-017 item 7, rev. 1): `BenchmarkParseAtCap` and the max RSS of `parse` on `build/cap-500k.fit` go into `MEASUREMENTS.md`. **v1.1:** both use the **all-caps file**: 500,000 records at 1 Hz with every stream, 100 sessions alternating `cycling` and `running` (so R-5 and R-7 work on every sample), 10,000 laps with `lap.sport`, 100,000 timer events, 1,000 `sport` messages and 256 field descriptions. The file must stay within `MaxBytes`; if it does not, reduce the timer events first and say so in `MEASUREMENTS.md`. Record decode and `Normalise` times separately. The v1.0 record-only row stays as history. If the max RSS exceeds 400 MB or decode plus normalise exceeds 2 s on the development machine, stop and report before hand-off.

**Normalisation is not under the deadline (D-16, QA-08-r1-5).** `workout` stays pure and takes no context. The budgets bound n (samples) and k (sessions + laps + timer events + hints), and `SampleCount` and `Normalise` must run in O((n + k) log(n + k)): no loop over sessions, laps, timer events or hints per sample. The all-caps measurement enforces it. QA measured 0.91 s of `Normalise` with 100 sessions against 0.12 s without, which comes from the per-sample session scan.

## Report

**`ReportV1` becomes report version 2** (`report_version: 2`); the Go type may keep its name or become `ReportV2`. Changes:

- New key `integrity` after `time_zone`, always written (E-7): `truncated`, `data_end` (only if truncated), `crc_failed`, `sequences`, `skipped_sequences`, `ignored_bytes`, in that order.
- `derived` gains, after the existing keys and omitted when `nil`: `elevation_loss`, `avg_speed`, `max_speed`, `avg_heart_rate`, `max_heart_rate`, `avg_cadence`, `max_cadence`, `avg_power`, `max_power`, `avg_temperature`, `max_temperature` (3 decimals, like totals).

- v1.1 adds no key and keeps report version 2 (version 2 has not been committed yet). Sport hints, sequence starts and legs are inputs or intermediate values; their effect is visible in `sport`, the streams, `derived` and `summary`.

It reads the file through `io.LimitReader(f, DefaultLimits.MaxBytes+1)`, so a huge file is not loaded whole, and parses with `NewParser(DefaultLimits, nil)`: no log lines, as before. **`corpus.sh`**: exit 0 as today; exit 3 is a rejection outcome. Its stdout is compared with the golden file exactly like a report, and the line ends in `rejected` instead of `bin … br …` (`ok     synthetic/course.fit  rejected`). Any other non-zero exit is `FAIL`. The header comment lists exit 3.

**`TestCorpus`**: parses with `NewParser(DefaultLimits, nil)`. An `*ingest.Error` gives `RejectionJSON` as the outcome to compare; invariants are checked only for accepted files. **`TestRoundTripCorpus` and `TestDataFileCorpus`** (datafile): a rejected file has no data file, and a stale golden data file for it is an error.
