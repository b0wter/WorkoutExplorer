# F-27 Reports API and operator delete command: architecture

- **Version:** 0.1
- **Status:** accepted (3 Nov 2026). Critical lane: what a report stores (I-7, NFR Privacy), deletion (I-4, AC-4), the Pushover exception. Includes the user decisions of 3 Nov 2026 (30-day retention, notifications in scope). OQ-101, OQ-102 open, not blocking (suggestions built unless the user objects)
- **Feature:** [`features/F-27-reports-api-and-operator-delete.md`](../features/F-27-reports-api-and-operator-delete.md); "AC n" is the n-th acceptance criterion there
- **Requirements:** INF-2, INF-3, NFR Privacy (store as little as possible; no data outlives its workout); TD invariants I-4, I-7, Data model (`reports`), Hosting and operations (Reports); decision log 1 Nov 2026 (report limit fixed at 60 per hour; notifications later)
- **Builds on:** [ADR-019](ADR-019-sqlite-store-schema-and-migrations.md) rev. 4 (this design adds item 10 and the every-pass checkpoint in item 9), [ADR-021](ADR-021-upload-request-handling-and-rate-limit.md) rev. 6 items 6 to 8 and 11, [ADR-022](ADR-022-private-workout-files-staging-and-recovery.md) item 6, [ADR-025](ADR-025-owner-api-access-and-not-found-response.md) items 5 and 8, [ADR-031](ADR-031-cross-process-lock-on-the-public-area.md), [F-12](F-12-owner-api.md) O-10 and its F-27 hand-off, [F-22](F-22-caching-and-security-headers.md) H-1, H-11, [F-31](F-31-server-deploy-and-monitoring.md) DP-4, DP-5, DP-6, DP-8, DP-14, [ADR-034](ADR-034-compose-bridge-networks-with-mounted-binaries.md) rev. 4; new: [ADR-039](ADR-039-report-notifications-through-pushover.md) (notifications)
- **Owner:** backend only (Go, `deploy/compose.notify.yaml`, `example.env`, runbook)

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| R-1 | **Package `internal/reports`** (the TD's proposed name, confirmed): the pure report rule (reason set, message rule) and the "file a report" operation behind a small port that `store` implements. `httpapi` → `reports`. The operator delete is a workout delete and lives in `lifecycle` beside `DeleteByOwner`. After a report is committed, `reports` hands it to the notifier port (R-11) | Reports never change a workout; keeping them out of `lifecycle` keeps that service about the workout's life |
| R-2 | **Schema v4, migration `0004_reports.sql`** (forward-only, ADR-019 item 5): see the SQL below. `workout_id` is the internal ID with **`ON DELETE CASCADE`**; `foreign_keys(ON)` is already on every connection (ADR-019 item 3). So every delete of a row removes its reports in the same statement: owner (F-12), expiry (F-21), operator (R-8), recovery's row removal (ADR-022 item 5) and any later path. `DeleteWorkout` is unchanged | Settles F-12's hand-off ("reports in `DeleteWorkout`'s transaction") by construction: no delete path can forget them, and an orphan report cannot exist. **Cost:** a later migration that rebuilds `workouts` (drop and rename, as `0003`) cascades into `reports` (ADR-019 item 10) |
| R-3 | **Stored per report: reason, message, time, the workout's internal ID, a row ID. Nothing else.** Not the client address in any form (also not hashed or salted: the limiter's key lives only in memory, ADR-021 item 8), no user agent, `Referer`, language or `public_id` copy (I-7, ADR-021 item 11). **Retention (user decision 3 Nov 2026):** a report goes when its workout's row goes (owner delete, expiry, operator delete), and **at the latest 30 days after it was filed**: `serve`'s expiry pass deletes reports with `created_at` at or before now − 30 days and checkpoints when it deleted any. A workout lives at most 30 days from upload and is reported only after publication, so today the first rule always fires first; the second holds if lifetimes ever change. Reports never outlive their workout (INF-2, AC 5; OQ-102). No "dismiss". Deleted bytes leave the files by `secure_delete` and the checkpoint (ADR-019 item 9). The message is never logged, published, sent to Pushover, or returned by any endpoint | INF-2, AC-4, NFR "no data outlives its workout" |
| R-4 | **At most 10 stored reports per workout.** A further valid report is answered like a stored one (`204`) and not stored (OQ-101). No global cap | The database's growth is not tracked while running (F-10 S-7); this bounds report text to about 40 KB per workout, and workouts are bounded by the storage cap and upload limits. A global cap would let one flood block reports on every workout |
| R-5 | **`POST /api/reports`**, checks in this order, cheapest and least revealing first: rate limit (R-6) → deadlines (read and write 30 s, as F-12 O-12) → `Content-Type` media type exactly `application/json` → body at most 16 KiB → one JSON object with keys `public_id`, `reason` and optional `message`, all strings, no other key, no duplicate, no `null` (the F-12 PATCH parsing rules) → `reason` in the set → message rule → one immediate transaction: the workout is unlisted and live (the SQL form of `Record.Live`, as `LivePublicIDs`, pinned by the same boundary test), else not found; then the R-4 count; then insert with `created_at` = now. A malformed `public_id` is not found without a query. Every request past the rate step counts (as ADR-021 item 7). **Message rule:** surrounding white space trimmed, then the F-12 description rule on the rest (at most 1,000 Unicode code points, no control characters other than line feed; F-12 itself does not trim); absent or empty is `''`. A `CHECK (length(message) <= 1000)` backs it up (SQLite counts code points too). **Reasons:** `spam`, `illegal_content`, `personal_data`, `other` | Validation before the lookup reveals nothing: a draft and an unknown ID give the same answer (AC 3, ADR-025). Requiring `application/json` means a cross-site page cannot post a report in a visitor's name without a CORS preflight, which Go never answers; no other CSRF measure |
| R-6 | **Rate limit:** an own instance of the upload limiter (ADR-021 items 6 to 8: same client address rule, IPv4 per address, IPv6 per /64, own process-local seed), **60 per rolling hour for both families as a constant, not a setting** (decision log 1 Nov 2026), table cap **10,000 keys**, fail closed. Memory ≤ 10,000 × 400 B = 4 MB, so F-31 DP-8's cap stays 1200m. A refusal is `429` with `Retry-After`; logged once per key as for uploads, without the address | One limiter type to keep correct. A full table refuses new reporters for at most an hour; a friends' site never gets near it |
| R-7 | **Listing reports.** The image is distroless (no shell, no `sqlite3`), so the operator runs `sqlite3` **on the host**, on the bind-mounted `/srv/workouts/workouts.db`, **read-only and as `app`'s UID**: `sudo setpriv --reuid=10001 --regid=10001 --clear-groups sqlite3 -readonly …` (DP-5; `sudo -u '#10001'` fails, the UID has no passwd entry). Root would be safe too: SQLite chowns side files it creates as root to the database's owner (tested, F-27 QA r1). The message is printed last as `quote(replace(message, char(10), '\n'))`, so it cannot forge an output line. **Never write with `sqlite3`**: the shell has foreign keys off and knows nothing of the files; a workout goes only through R-8. The runbook's query joins `workouts` for `public_id`, title, state and expiry and formats times with `datetime(…, 'unixepoch')`. The host needs the `sqlite3` package (runbook, fresh VPS) | What the spec asks (TD Hosting: `sqlite3`), with no more rights than `serve` has. A list subcommand would avoid the host package but is code nobody asked for |
| R-8 | **`workout-explorer delete -data <dir> [-y] <public_id>`.** Production: `docker compose exec app /srv/workout-explorer/bin/workout-explorer delete -data /srv/workouts <public_id>` (`docker compose run --rm app delete …` while `app` is stopped). It opens an **existing** `workouts.db` only (missing: exit 1, never created) and **refuses a database whose schema version is not the binary's** (no migration from an operator command; `serve` migrates at start). It reads no `WORKOUT_EXPLORER_*` setting. It finds the row by `public_id` in **any state** (draft, unlisted, past its deadline: INF-3 "any workout"), prints `public_id`, state, created and expiry times, title and number of reports, and asks `Delete? [y/N]` on a terminal; `-y` skips the question; no terminal and no `-y` is a usage error. Then `lifecycle.Service.Delete` unchanged (row with its reports, then `public/{public_id}` under the ADR-031 lock, then `private/{id}`), then the checkpoint, and the F-12 O-10 line with `by` = `operator`. **Fast removal:** nothing to purge. Caddy has no cache and reads the disk per request (F-22 H-1, H-11), so the page is gone when its folder is | Same path as every other delete (I-4, AC 6). The question shows what the ID points at before an irreversible step on a server without backups |
| R-9 | **Exit codes.** `0` deleted (also when the checkpoint was busy: warning printed, R-10 covers it). `1` not deleted or not completely: database or file error, or the operator answered no; the message says which. After a partial delete the public folder goes at `serve`'s next sweep (within about a minute, F-21), the private folder at `serve`'s next start (ADR-022 item 5). `2` usage: flags, arguments, malformed `public_id`, no confirmation possible. `3` no workout with this ID, including a repeat of a completed delete | Scripts can tell "already gone" from "failed"; a repeat is harmless (idempotent effect) |
| R-10 | **Cross-process rules** (the command is a second process beside `serve`). SQLite's `busy_timeout` covers the database; ADR-031's lock covers `public/`; `serve`'s post-hook re-check (F-12 hand-off, F-15 P-6) removes a folder that a concurrent owner edit rebuilt after the row went. **`serve`'s expiry pass checkpoints on every pass**, not only after its own deletes, so another process's delete (this command, F-30) leaves the WAL within one pass (ADR-019 item 9 note). **Accepted:** `serve`'s in-memory storage total keeps the deleted bytes until its next start, which can only close uploads early (as F-10 S-7); restart `app` if it matters | An admin endpoint inside `serve` would avoid the second process but add an authenticated surface to the public API for one operator command; the process boundary is already solved |
| R-11 | **Notifications through Pushover, opt-in** ([ADR-039](ADR-039-report-notifications-through-pushover.md)): settings `WORKOUT_EXPLORER_PUSHOVER_TOKEN` and `_USER` (both unset: off, the default; one only or a malformed value: exit 2); message `New report #<id>: <reason>`, never the link, `public_id`, title, reporter's text or request data; sent after commit from a bounded queue by one goroutine, 10 s timeout, no retry, so a report never fails or waits on Pushover; at most 10 per rolling hour per process, the rest counted into the next message; egress for `app` only through the override `compose.notify.yaml` | The per-client limit (60 per hour) does not bound notifications across many addresses; the global cap keeps the phone quiet and within Pushover's free quota. The link is the workout's access and stays off third parties |

**Schema v4** (load-bearing; `TestSchema` pins it):

```sql
CREATE TABLE reports (
    id         INTEGER PRIMARY KEY AUTOINCREMENT, -- numbers never reused (ADR-039 item 2)
    workout_id TEXT    NOT NULL REFERENCES workouts (id) ON DELETE CASCADE,
    reason     TEXT    NOT NULL CHECK (reason IN ('spam', 'illegal_content', 'personal_data', 'other')),
    message    TEXT    NOT NULL DEFAULT '' CHECK (length(message) <= 1000),
    created_at INTEGER NOT NULL
) STRICT;
CREATE INDEX reports_workout_id ON reports (workout_id);
```

**Responses** (JSON, `Cache-Control: no-store`, through `respond.go`):

| Status | `error` | When | `message` |
| --- | --- | --- | --- |
| `204`, no body | — | stored, or not stored under R-4 | — |
| `400` | `invalid_report` (new, like `invalid_settings`) | content type, body size, JSON shape or types, reason, message rule | one fixed plain sentence per cause, for F-28 to show as is |
| `404` | `not_found` | unknown or malformed ID, draft, past its deadline | ADR-025 item 5 body, byte-identical |
| `429` | `rate_limited` (existing code) | R-6, with `Retry-After` | "Too many reports. Please try again later." (the upload sentence is UP-10's and stays) |
| `500` | `server_error` (existing) | anything else | existing sentence |

Logging: one INFO line `report stored` with the report's `id`, the workout's internal `id` and `reason`; never the message or `public_id`. Notification failures as ADR-039 item 3. Refusals other than the first rate refusal per key are not logged (ADR-025 item 8).

## Verification (critical lane, QA effort high)

- AC 1, AC 4: the schema check pins `reports`' columns; the request-metadata check of F-09 is extended to a report sent with `X-Forwarded-For`, user agent and `Referer`: none appears in the database files or the log.
- AC 5: F-12's end-to-end list of places holding workout data gains `reports`, for owner, expiry, operator delete and recovery's row removal; F-21's byte scan of `workouts.db`, `-wal` and `-shm` includes a stored report message, also after an operator delete while `serve` runs.
- R-5 boundary: a report at the exact deadline is not found; the SQL and `Record.Live` stay pinned together. R-3: a report filed 30 days ago is gone after one expiry pass, a younger one stays.
- R-11 against a local fake Pushover: settings matrix (none, one, both, malformed: exit codes, no value in any output); the request carries only ADR-039 item 2's fields; a hanging or failing fake neither delays nor changes the `204`; the eleventh notification in an hour is folded into the next; no secret in any log line, also on failure. Once in the Compose setup (manual): without the override `app` cannot reach the internet; with it, a real notification arrives.
- R-8, R-9 once in the Compose setup (manual): `exec` with a terminal asks; `-y` without one deletes; the page answers the generic `404` through Caddy within 60 s; a repeat exits 3; R-7's command works on the VPS and leaves no root-owned file in `/srv/workouts`.

## Open questions (product; the user answers by number)

| ID | Question | Suggestion | Blocks |
| --- | --- | --- | --- |
| OQ-101 | Reports per workout are capped at 10 (R-4). Answer a further report as received without storing it, or refuse it with a message? | **Answer as received, do not store.** The operator already has ten reports on that workout; the reporter needs no new error state in F-28. Cost: an 11th reporter's message is lost. Alternative: `409` "This workout has already been reported." | Nothing (suggestion built unless the user objects) |
| OQ-102 | The 30-day retention "so reports survive a long holiday": should a report outlive its workout? | **No.** Keep INF-2 "deleted with their workout"; the notification reaches the operator on holiday, and once the workout is gone there is nothing to act on. Outliving would drop the foreign key, keep a `public_id` copy, and keep a reporter's text (possibly someone else's personal data) after the content it is about; it changes INF-2, F-27 AC 5 and the NFR "no data outlives its workout" | R-2, R-3 only if the answer is yes |
