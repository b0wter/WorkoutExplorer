# ADR-021 Upload request handling: streamed multipart in memory, size cap while reading, in-memory rate limit by hashed client address

- **Status:** accepted
- **Date:** 16 Oct 2026; revision 4 of 22 Oct 2026; revision 5 of 1 Nov 2026 (item 6: trusted proxy address, F-31 Compose bridge network); revision 6 of 1 Nov 2026 (items 6 to 8: Caddy behind the operator's proxy, two limit settings, F-31 v0.3). The "(rev. N)" tags mark where a rule was introduced
- **History:** [architect/history/ADR-021-upload-request-handling-and-rate-limit.md](history/ADR-021-upload-request-handling-and-rate-limit.md)
- **Features:** F-09 (introduces it), F-10 (storage gate in the same check order), F-11 (shows the messages), F-27 (reuses the limiter for reports), F-31 (Caddy in front)
- **Supersedes:** none
- **Requirements:** UP-1 (20 MB = 20,000,000 bytes), UP-10 (messages), NFR Security (size and rate limits, "a malformed or hostile file can fail only its own upload"), NFR Privacy (store as little as possible), TD Security and privacy (Uploads: "20 MB cap enforced while reading, rate limit of 60 uploads per hour per IP address (kept in memory, not stored)"), F-09 AC 3, AC 4, AC 5; ADR-017 (parse limits), ADR-018 (kinds and messages)

## Context

`POST /api/workouts` is the only unauthenticated endpoint that takes real work: a body of up to 20 MB, a parse, two file writes and a row. Go's convenient `r.ParseMultipartForm` writes every file part above its memory threshold to the OS temp directory, so the upload would land on disk outside our data directory, outside the cleanup rules, and possibly outlive a rejection. The Go process sits behind Caddy, and in production Caddy behind the operator's reverse proxy (F-31), so `RemoteAddr` is Caddy's address (loopback in local runs, Caddy's container address in production); the client address arrives in `X-Forwarded-For`. The spec counts per "IP address", which for IPv6 is a weak identity: one subscriber holds a whole /64.

## Decision

1. **Upload cap: 20,000,000 bytes of file content** (`httpapi.MaxUploadBytes`), decimal megabytes as in ADR-002, so "20 MB + 1 byte" is 20,000,001 bytes and F-11's browser check uses the same number. It is below `ingest.DefaultLimits.MaxBytes` (20 MiB), which stays as the parser's own guard; a test asserts the order. Whole request body cap: `MaxUploadBytes` + 16 KiB for multipart framing (`maxBodyBytes`).
2. **Read the body as a stream, never through `ParseMultipartForm`.** `r.MultipartReader()`; the first part must be form field `file`; its bytes are read into memory through `io.LimitReader(part, MaxUploadBytes+1)`; then `NextPart` must return `io.EOF`. The body itself is wrapped in `http.MaxBytesReader(w, r.Body, maxBodyBytes)`. A request whose `Content-Length` already exceeds `maxBodyBytes` is refused before a single body byte is read. Nothing of the request touches the disk until the parse has accepted the file.
3. **Order of checks, cheapest and least revealing first:** (F-10: storage gate) → in-flight cap → rate limit → deadlines → content type → `Content-Length` → read the part → parse (ADR-017) → store (ADR-022). A request refused before the rate-limit step does not count against the limit.
4. **In-flight cap: N uploads at once per process** (reading, parsing, stripping and storing). N is a server setting (rev. 1, user decision):
   - It comes from the environment variable **`WORKOUT_EXPLORER_MAX_CONCURRENT_UPLOADS`**, read once by `serve` at start in `cmd/workout-explorer` and passed to `httpapi` as `Config.MaxConcurrentUploads`. No other package reads the environment.
   - Unset or empty: **4**.
   - Otherwise the value must be ASCII digits without sign, spaces or leading zero (`^[1-9][0-9]*$`) and between **1 and 16**.
   - Anything else makes `serve` print `serve: WORKOUT_EXPLORER_MAX_CONCURRENT_UPLOADS must be a whole number from 1 to 16` to stderr and exit 2 before opening the database or listening. A typo in the unit file fails loudly instead of silently running with the default.
   - The effective value is logged in the `server started` line (`max_concurrent_uploads`).
   - The upper bound keeps memory bounded (rev. 2). An upload holds at most 20 MB while it waits, and more while it is parsed and encoded. The process's worst case is M(N) ≤ 2·A + (N − 2)·B (ADR-017 rev. 3 item 4).

   An upload past the cap gets `503` with `Retry-After: 30` and UP-10's "Too many uploads right now. Please try again in a minute."
5. **Deadlines per request** with `http.ResponseController` (F-01 left the server-wide timeouts unset for this): read deadline 120 s and write deadline 120 s + 6·T (180 s at the default T, rev. 4 below) from the start of the handler. `http.ErrNotSupported` (test recorders) is ignored. The parse runs with the request context, so a client that disconnects cancels it (ADR-018 `canceled`).

   **(rev. 4) The write deadline follows the parse time limit.** It is **read deadline + 6 × T**, where T is the parser's time limit (ADR-017 rev. 7, `WORKOUT_EXPLORER_PARSE_TIMEOUT`). At the default T = 10 s, that is 180 s, as before. At 60 s, it is 480 s. `cmd` passes the parser's effective T as `Config.ParseTimeout`, and `httpapi` computes the deadline at step 3. The read deadline stays 120 s, because reading the body does not depend on parsing.
   - The basis is the worst-case wait. A friend's upload can read its body for up to 120 s. It can then wait up to one `Accept` for a parse slot, behind two crafted files, and run its own `Accept`. Each `Accept` is at most 2·T plus normalisation and the strip (ADR-017 rev. 2 item 2). That uses 4·T of the 6·T; the remaining 2·T covers normalisation, the strip, encoding and storing, and it grows with T as a slower machine needs.
   - With a fixed 180 s, a T only a few seconds above the default could make that upload finish after its write deadline: 4·T alone uses the whole 60 s margin at T = 15 s. The draft would be stored (OQ-45) but the response lost.
6. **Client address:** if the direct peer is a **trusted proxy** and `X-Forwarded-For` is present, the client is its **last** comma-separated entry (the one Caddy appended); otherwise the peer address. **(rev. 5) A trusted proxy is a loopback address, or exactly the one address in `WORKOUT_EXPLORER_TRUSTED_PROXY`** (F-31 DP-1a). That setting is one IP address, not a list or prefix, and is compared after unmapping; it is read by `serve` only. Unset means loopback only. An invalid value makes `serve` exit 2, by the TD Configuration rule. In production it is Caddy's fixed address on the Compose `backend` network. **(rev. 6)** Caddy itself trusts the header only from the operator's proxy and sends Go the client it resolved as the only entry (F-31 DP-1b), so the last entry is the client, never the operator's proxy. An unparsable entry falls back to the peer. A peer that is not a trusted proxy can never choose its address through the header. IPv4-mapped IPv6 is unmapped. **IPv6 addresses count per /64 prefix**; IPv4 per address.
7. **Rate limit per rolling hour per client key** (`RateWindow`). **(rev. 6) Two settings**, read by `serve` by the TD Configuration rule (invalid → exit 2) and passed in `Config`: **`WORKOUT_EXPLORER_UPLOADS_PER_HOUR_IPV4`** (per address) and **`WORKOUT_EXPLORER_UPLOADS_PER_HOUR_IPV6`** (per /64), each default **60**, range **1–240**, both logged in `server started`. Sliding log: per key the times of the allowed attempts in the last hour, at most that key's family limit. **Every request that passes the rate-limit step counts**, also when it is then refused for size or by the parser: the limit protects the parse, which a rejected file costs too (confirmed by the user, OQ-41). A refused attempt (429) does not extend the window. The response is `429` with `Retry-After` = whole seconds until the oldest counted attempt leaves the window.
8. **The limiter never holds an address.** The key is `hash/maphash` of the (prefix-masked) address bytes with a random seed made at process start: 64 bits, process-local, not reversible without the seed, gone on restart. The table holds at most 100,000 keys; expired keys are swept when 10 min have passed since the last sweep, or when the table is full and at least 1 min has passed since the last sweep (rev. 2: a full table under attack would otherwise be scanned on every request). If the table is still full, new keys are refused with `429` (fail closed), and one WARN line is logged per sweep. Restarting the process resets all limits; that is accepted.

   **(rev. 3) Per-key representation and memory bound.** An IPv6 /48 alone supplies 65,536 /64 keys, so the cap is cheap to fill, and a log of `[]time.Time` held about 185 MB at the cap (QA-09-r1-4). The log is:
   - **Times as whole seconds since the limiter's epoch**, `uint32` (the epoch is `now()` at `newLimiter`; 136 years of range). A time is stored **rounded up** to the next whole second, and an entry expires once `now ≥ stored + window`. So an attempt counts for at most 1 s longer than the window, never shorter. "60 per rolling hour" still holds, with the error on the strict side. `Retry-After` stays whole seconds, rounded up.
   - **One backing array per key, allocated once** with `make([]uint32, 0, limit)` when the key is first seen, `limit` being its family's (item 7). Expired entries are removed by copying the live ones down to index 0 (`copy`), never by reslicing forward, so `append` never reallocates.
   - Per key, that is the 4·`limit`-byte array, a small struct (slice header and the `refused` flag) and the map slot. **Bound: at most 4·`limit` + 160 bytes per key, including the map** (400 at 60). **(rev. 6)** Both families share the one table and its 100,000-key cap, so **L ≤ 100,000 × (4·max + 160) bytes**: 40 MB at the default 60, **112 MB at the maximum 240**. F-31 sizes the memory cap with the maximum (DP-8). `TestLimiterMemory` proves the bound at 60 and at 240 (F-09 design, Tests).

   The cap stays at 100,000 keys. A lower cap would shrink L further, but the table would fill sooner, and a full table refuses every new client (fail closed). That trade is not worth making for memory that is now bounded and counted.
9. **Responses are JSON with `Cache-Control: no-store`.** Success `201` with `{"view_url": "/w/…", "edit_url": "/edit/…#…"}` and nothing else (ADR-020). Failure `{"error": "<code>", "message": "<sentence>"}`; the browser shows `message` as it is (F-11). The sentences for refusals that are not about the file's content are UP-10's, exactly. Codes and statuses are in the F-09 design, section `POST /api/workouts`. Parser rejections keep ADR-018's kind as the code and its `Message()` unchanged.
10. **No cross-site request protection is added.** The endpoint carries no ambient credential (no cookies, no accounts); a forged cross-site upload can only spend the victim's own rate budget.
11. **What is never stored or logged** (TD invariant I-7): the client address in any form (also not hashed in a log), `X-Forwarded-For`, user agent, the multipart file name and content type, `Referer`, and the upload's duration in the database. Log lines from the upload path use an allow-list of keys (F-09 design, Logging).

## Consequences

- Memory (rev. 2): M(N) ≤ 2·A + (N − 2)·B, with A and B from ADR-017 rev. 3 item 4. The default N = 4 gives 2·A + 2·B. F-31 sizes the container's memory cap, and `GOMEMLIMIT` if used, from the measured M(N) (F-09 design, section Tests, server run).
- (rev. 3, rev. 6) The rate table adds at most L (item 8), 112 MB at the settings' maximum. The server run does not fill the table, so F-31 adds that L to the measured M(4) (ADR-017 rev. 4, F-31 DP-8). F-27's limiter instance adds its own bound: its cap × its per-key bound at its limit.
- The binary's settings are environment variables listed in the TD (Conventions, Configuration), all by the same rules (ADR-017 rev. 7). A flag (`-max-concurrent-uploads`) would have matched the existing convention; the user asked for environment variables.
- (rev. 4) A configured parse time limit does not change the in-flight cap, `Retry-After: 30` for `busy`, the rate limit or memory (ADR-017 rev. 7 item 5). F-31 keeps every proxy timeout in Caddy at or above the write deadline, which is 120 s + 6·T.
- A refused request with a large body is answered without reading it; Go's server drains at most 256 KiB and then closes the connection. A browser may report this as a network error rather than show the `413` body; F-11's own size check runs first, so this only affects clients that skip it.
- Limits live in one process's memory. A deploy restart forgives every limit; acceptable for a friends-only site, and storing them would contradict the TD.
- F-27 reuses the same limiter type with its own instance and limit (report rate, F-27 design).

## Would choose differently if

- Uploads are seen failing on slow phone connections at the 120 s read deadline (real files are mostly a few MB): raise it, keeping the in-flight cap.
- Abuse from many addresses shows up (the in-flight cap or the key table fills): move the limit in front, into Caddy, and keep this one as the backstop.
- Abuse is seen from many addresses inside one /64 being treated as one (an institution's network): the mask length is one constant.
