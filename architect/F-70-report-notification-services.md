# F-70 Report notifications through other services: design

- **Version:** 0.2 (24 Nov 2026). **Status:** accepted. History: [history/F-70](history/F-70-report-notification-services.md)
- **Lane:** critical (delete links are credentials going to a new destination; new secrets). **Owner:** backend
- **Feature:** [F-70](../features/F-70-report-notification-services.md). Its Scope and acceptance criteria are not repeated here
- **Requirements:** INF-4, INF-6, INF-8, INF-1; NFR Privacy, NFR Security; TD I-7
- **Depends on:** [ADR-039](ADR-039-report-notifications-through-pushover.md) (items 3 to 5 stay as they are), [ADR-042](ADR-042-report-delete-keys.md), [F-37](F-37-report-notification-links.md) DK-1 to DK-10, [F-52](F-52-auto-update.md) AU-11, [F-60](F-60-bare-metal-auto-update.md)
- **Changes:** ADR-039 item 6 ("no callback abstraction"), ADR-042 item 6, F-37 DK-3 (last sentence) and DK-5 (see "Documents to update")

## Decisions

| ID | Decision | Why |
| --- | --- | --- |
| NS-1 | **One notifier, three request builders.** `internal/pushover` becomes `internal/notify`. It holds the parts every kind shares: the queue, the hourly limit, the `(+N more)` folding, issuing the key through the issue function, the HTTP client, the failure classes and the WARN line. Each kind adds only one unexported builder that turns `{report, reason, more, view_url, delete_url}` into one `*http.Request`. The port `reports.Notifier` (`Notify(id, label, viewURL)`) does not change, and `reports` never learns the kind | Delete keys, limits and logging rules stay in one place, so a new kind cannot weaken them. A new kind means one builder plus one setting rule |
| NS-2 | **Settings, read only by `serve` in `settings.go`, once at start.** A setting that is empty counts as unset. `_KIND` must be `ntfy` or `callback`. `_KIND` and `_URL` are set together or not at all. `_TOKEN` needs both of them. Pushover settings together with `_KIND` exit 2 and name both. The exit-2 messages are fixed text naming the setting. They never include the value or the error text from `url.Parse`, because that text contains the URL | The TD Configuration rule. Go's URL errors echo their input |
| NS-3 | **URL format:** at most 2,048 bytes; only RFC 3986 characters (letters, digits, `-._~:/?#[]@!$&'()*+,;=%`), so no space, `"`, `\` or control character; `url.Parse` must succeed; the scheme is `https`, or `http` only when the host is a **literal IP** with `IsLoopback()` or `IsPrivate()` (Go `netip`: 127/8, ::1, 10/8, 172.16/12, 192.168/16, fc00::/7). A host name with `http` exits 2. No userinfo and no fragment. ntfy: the path names a topic (not empty and not `/`). **Token:** 1 to 256 characters of RFC 7235 token68 (`A-Za-z0-9-._~+/` followed by optional `=`), which covers ntfy's `tk_…` | A name can later resolve to a public address, and over `http` the delete link would then cross the internet in clear text. The character set lets the shell updater pass the URL to curl without escaping (NS-11) |
| NS-4 | **Pushover:** the request stays byte-identical to today (DK-10) | AC 45 |
| NS-5 | **ntfy:** `POST` to the configured topic URL. Body in plain text: `New report #12: Personal data (+3 more)`. Headers: `Title: Workout Explorer`; `Click: <view_url>`; `Actions: view, Delete this workout, "<delete_url>"`, sent only when a key was issued; `Authorization: Bearer <token>` when a token is set. No `Markdown`, `Priority`, `Tags`, `Cache` or `Firebase` header. **The delete link appears only in the action, never in the body** | Android shows the title, the body and the button label on the lock screen, never the action URL (F-37 AC 41). Headers let us post to exactly the configured URL without splitting off the topic. All values are ASCII (Go is English only, ADR-059); a label that is not ASCII would need RFC 2047 encoding. With the default cache, ntfy.sh keeps the message for 12 h, readable by anyone who knows the topic, and that person would have received it live anyway (the topic is the secret, NS-8) |
| NS-6 | **Callback:** `POST` to the URL. `Content-Type: application/json`, plus `Authorization: Bearer <token>` when set. The body is exactly the feature's fixed object in this key order: `report`, `reason`, `more` (always present), `view_url`, and `delete_url` (left out when no key was issued). No other field, no templating | Feature Scope "Callback body" |
| NS-7 | **Delivery (all kinds):** one shared client with a 10 s timeout, no proxy from the environment, the system CA bundle, and **no redirect followed** (`ErrUseLastResponse`), so any 3xx is a failure. Success is any 2xx. The response is read up to 4 KiB and discarded. A failure is one WARN line `notification failed` with `kind` and either `status` or a fixed `class` (`timeout`, `network`, `request`), without retry. **A failed send revokes the key issued for that report** (clear the hash of that report ID, best effort, with its own short deadline so it also runs at shutdown) | AC 47 ("no delete key issued for that report"). An endpoint that answered 5xx or 3xx may still have logged the link, so a key that was never confirmed delivered is not left valid. This replaces DK-3's "a failed send keeps the key", for Pushover too. Cost: an endpoint that delivered and then answered with an error leaves the operator a dead link, and the CLI remains |
| NS-8 | **Logging and disclosure.** `server started` logs `notify` (`pushover`, `ntfy`, `callback` or `off`) and `notify_host` (host and port; ntfy and callback only). **Never logged or shown:** the URL's path, query or whole value, the token, the Pushover keys, the delete link, the viewing link, the response body, or Go error text. The About page names Pushover; for ntfy, "ntfy" and the host, inserted as escaped text; for a callback, "the operator's own server" (no host). The path never appears, because on a public ntfy server the topic in the path is the secret | Feature Scope "Secrets". The host is needed for diagnosis and for INF-1 (whether a visitor's report link goes to ntfy.sh or to the hoster's own server) |
| NS-9 | **SSRF stance:** the URL is operator configuration in a `0600` env file, as trusted as the binary. Nothing a viewer, sharer or reporter sends picks the destination or a header. The body holds only the NS-5 and NS-6 fields, and responses never come back to anyone. **Checked:** NS-3 only. **Not checked:** where an `https` host resolves (private and LAN targets are a goal of the feature), DNS rebinding, ports | Address filtering would block the self-hosted ntfy use case and protect nothing that the person writing `.env` cannot already reach |
| NS-10 | **Egress (feature constraint).** Compose and Podman: unchanged, `compose.notify.yaml` or the egress drop-in. That route reaches the LAN and the internet alike; Docker cannot narrow it without host firewall rules, which we do not ship. Inside a container, `127.0.0.1` is the app itself, so a service on the same host is reached through its LAN or bridge address. Bare metal: loopback already works without a drop-in (`IPAddressAllow=localhost`). For a LAN service the hoster writes their own drop-in `notify-lan.conf` with `IPAddressAllow=<address>` instead of `notify.conf`; only `notify.conf` is byte-compared by `deploy.sh` | "Reachable without opening the app to the internet if the design can manage it": bare metal can, containers cannot without a firewall we would have to maintain |
| NS-11 | **Updater (`update.sh`, F-52 AU-11).** `alert()` reads the same five settings from `.env` as data (it never sources the file). It applies the NS-2 and NS-3 rules: the same accepted set as Go, with `http` allowed only to a literal loopback or private IPv4 address, `[::1]` or a `[fc..`/`[fd..` address. Two services, or an invalid value: one line `notification settings invalid; no alert`, and the update result is unchanged. Bodies: Pushover as today; ntfy with the alert text as body and the `Title` header; callback `{"alert":"<text>"}`. The text holds fixed words and a validated tag, with no `"` or `\`. curl: `-q -fsS --max-time 10 -o /dev/null`, no `-L` (no redirects), `--noproxy '*'`, `--proto =https`, or `=http` only under the exception. **The URL and the token reach curl only through `-K -` (its configuration on stdin), never on the command line**, and so never in `ps` | The server may be down exactly when the updater alerts, so the updater cannot ask the server. Two validators must agree; the engineer keeps one list of cases that both test suites run. The `alert` key tells receivers an updater alert apart from a report |
| NS-12 | **Revocation:** `serve` with no service set clears every delete key at start (DK-5, renamed from "without Pushover" to "notifications off"). A change of service, URL or token clears them too (NS-13) | Feature Scope "Revocation", AC 49 |
| NS-13 | **Automatic revocation on a change** (user, F70-Q1, 24 Nov 2026; changes OQ-344). `serve` computes `HMAC-SHA256(salt, kind ‖ URL ‖ token ‖ Pushover token ‖ Pushover user)`, with `off` as the value when nothing is set. It is stored with a 16-byte random salt in `{data}/notify.state` (mode 0600, written to a temporary file then renamed; the salt is made once and kept). At start: if the stored value differs or the file is missing, clear every key, **then** write the file. A crash between the two steps clears again at the next start. A file, not a schema change (ADR-019 is a one-way door). The first start after the upgrade revokes the delete links still out, once | Plain text holds no secret. A salted hash of a weak ntfy topic can still be guessed offline from the data directory, but the originals stored there are worth more than the topic. Cost: one file and one comparison |

## Tests that the design depends on

Each kind runs against a local fake endpoint; none contacts a real service (AC 50). Required checks:

- A byte scan of every log line, every exit-2 message and the About page finds no URL path, token or key.
- A redirect sends exactly one request, and the key ends with `NULL`.
- Pushover's form output is unchanged against today's test vectors.
- `update.sh` never shows the URL or the token on a command line (as for the Pushover secrets today).
