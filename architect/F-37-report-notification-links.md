# F-37 Report notification links: architecture

- **Version:** 0.1
- **Status:** accepted, built (9 Nov 2026). Critical lane: a new credential that deletes data. OQ-114 to OQ-119 built as accepted (one invalid message, OQ-115's alternative chosen: a key only for a sent notification, no reporter's message, 30 days, risk of the operator's Pushover account accepted). OQ-125 resolved 9 Nov 2026 (the delete link from the notification works on the phone, so the fragment is kept)
- **Feature:** [`features/F-37-report-notification-links.md`](../features/F-37-report-notification-links.md); "AC n" is the n-th acceptance criterion there
- **Requirements:** INF-4 (changed 9 Nov 2026), INF-6, INF-1, INF-3, AC-4, SH-10, NFR Security, NFR Privacy
- **Builds on:** [F-27](F-27-reports-api-and-operator-delete.md) R-2, R-3, R-6, R-8, R-11; [ADR-039](ADR-039-report-notifications-through-pushover.md) rev. 1 (item 2 rewritten by this design); [ADR-020](ADR-020-workout-identifiers-edit-token-and-links.md) items 2 to 4, 7, 9; [ADR-025](ADR-025-owner-api-access-and-not-found-response.md) items 2, 3, 7, 8; [ADR-021](ADR-021-upload-request-handling-and-rate-limit.md) items 6 to 8; [ADR-019](ADR-019-sqlite-store-schema-and-migrations.md) items 5, 10; [ADR-024](ADR-024-upload-page-plain-typescript-entry.md); [ADR-032](ADR-032-response-headers-in-caddy.md); [F-29](F-29-about-page-and-attributions.md) AB-2, AB-3, PT-9. ## Decisions

| # | Decision | Why |
| --- | --- | --- |
| DK-1 | **The delete key is a Reports concept.** `reports` issues, looks up and redeems keys behind its `Store` port, and deletes through a new port that `lifecycle.Service.DeleteByOperator` satisfies unchanged. `pushover` stays an adapter: it gets a key-issuing function at wiring and never touches the store. `httpapi` maps the two routes (DK-6). Absolute links come from `WORKOUT_EXPLORER_BASE_URL` (already required by `serve`): viewing link `lifecycle.ViewPath`, **delete link `/report-delete#{key}`**, built only in `reports` | One owner per concept; the notifier keeps its one job; no new delete path (I-4) |
| DK-2 | **Key: 16 bytes from `crypto/rand`, base62 fixed 22 characters, stored only as SHA-256 of its ASCII** (the edit token's encoder and `HashToken`, ADR-020 items 3, 4). **Stored as the nullable column `reports.delete_key_hash`**, unique where not null (schema below; ADR-042) | The key lives exactly as long as its report: cascade on every workout delete (F-27 R-2) and the 30-day prune (R-3) remove it by construction, with no new table or cascade to forget |
| DK-3 | **A key is created only for a notification actually sent:** the sender goroutine, after the hourly cap admits a message and right before the request, asks `reports` to issue the key for that report. Reports folded into `(+N more)`, dropped from a full queue, lost to a restart, or gone before sending get none (OQ-115). Issue fails or finds no report: the message goes without the delete link, one WARN line with the report ID only. A failed or timed-out send keeps the key (Pushover may have it). The plain key exists only in that goroutine and the outgoing request body | Stores nothing that cannot be used. **Deviation:** INF-6 says "each stored report gets its own delete key" (hand-off) |
| DK-4 | **Valid** while: a report row holds the key's hash, that report was filed less than 30 days ago (not shortened), and its workout row exists with `expires_at` after now (an expired, unswept workout is gone, as ADR-025 item 4). Reports come after publish, so the workout always expires first; the 30 days are a backstop if lifetimes change. The page shows the workout's `expires_at` as the expiry | 7 days would only lose the phone shortcut during the long holiday the 30-day retention was chosen for (OQ-117) |
| DK-5 | **Pushover off: `serve` clears every `delete_key_hash` at start** (one statement). The routes stay registered and answer the invalid response, since no key matches | INF-6 "without notifications, no keys exist" holds after the operator turns them off. It is also the **revocation path**: a lost phone or a leaked Pushover account → restart `app` without the two settings |
| DK-6 | **Routes.** `GET /report-delete` (Caddy, static page, DK-11); `GET /api/report-delete` = lookup, no side effect, also when repeated; `POST /api/report-delete` = redeem. Check order for both: rate limit (DK-9) → any query string → the ADR-025 item 2 Bearer parser (absent, two headers, other scheme, not 22 base62: invalid) → store. **POST reads no body and checks no `Content-Type`:** the `Authorization` header is the CSRF barrier (ADR-025 item 7: a form cannot set it, a cross-site `fetch` needs a preflight Go never answers). This is AC 39's "architect's equivalent". No public ID anywhere in the request, so a key can only reach its own workout (AC 34) | The edit token's transport, proven and redacted by Caddy if logging is ever enabled (ADR-020 item 9) |
| DK-7 | **Lookup answers `200` with exactly:** `title` (the stored title, or the default title made in Go from the row's sport, start time and offset by `page`'s existing rule, never re-implemented in the browser), `start_date` (text, workout's own zone as on the page), `report_id`, `reason` (label, DK-10), `filed_at`, `expires_at` (Unix seconds, formatted in the browser), `report_count`. Never the public ID, internal ID, description, any reporter's message (OQ-116) or another report's fields | What INF-6 lists, nothing more; the page needs no second request |
| DK-8 | **Redeem = one consuming statement, then the operator delete.** One `UPDATE … SET delete_key_hash = NULL … RETURNING` with the DK-4 conditions yields the workout's internal and public ID, or no row (invalid). Then `DeleteByOperator` unchanged: row with its reports (and so every other key of the workout), public folder under the ADR-031 lock, private folder, checkpoint, `workout deleted` with `by` = `operator` (logged only by the call that removed the row, QA-37-r1-1). `204`. Single use is the consume: of two concurrent confirms (also across processes) exactly one proceeds. A delete error after the consume answers `500` like the owner delete; the key is spent and the operator uses `workout-explorer delete` (leftovers as F-27 R-9) | Single use cannot depend on the delete succeeding or on an in-process lock. **Cost:** a database failure in the delete wastes the key; accepted, the CLI remains |
| DK-9 | **Rate limit:** an own instance of the upload limiter type (ADR-021 items 6 to 8 client rule), **30 per rolling hour** per IPv4 address or IPv6 /64, lookup and confirm counted together, every request counts, a constant; table cap **1,000** keys (≈ 0.4 MB, F-31 DP-8 unchanged), fail closed. Refusal `429` `rate_limited` "Too many requests. Please try again later." with `Retry-After`, logged once per key without the address | The only legitimate client is the operator (two requests per link). 128-bit keys need no guessing guard; the limit bounds database work (AC 38). **Cost:** many addresses can block the phone path for an hour; the CLI is unaffected |
| DK-10 | **Pushover request** (ADR-039 item 2 rev. 1): `title` unchanged; `html=1`; `message` = `New report #<id>: <Label>` plus ` (+N more)` as before, a line break, and `<a href="<base>/report-delete#<key>">Delete this workout</a>` (only when DK-3 issued a key); `url` = `<base>/w/<public_id>`, `url_title` = `Open workout`. Labels in one table in `reports`: Spam, Illegal content, Personal data, Other, used by the message and DK-7. Never the title, reporter's message or request data | Pushover strips HTML in the system notification and shows only the anchor text there, so **the key is not printed on the lock screen**; in the app the anchor is tappable. A plain auto-linked URL would print it. `url` is Pushover's tap target |
| DK-11 | **Confirmation page:** `src/web/report-delete.html`, a further Vite entry in plain TypeScript with the plain theme, like the upload page (ADR-024: no Svelte, no chunk shared with the activity entry; own ceiling 4,000 bytes gzip under ADR-002). Reads the key from the fragment (up to the first `&`, ADR-020 item 7), looks up, shows DK-7, "Delete workout" posts, then "The workout has been deleted."; any `404` shows the server's sentence as is. `<noscript>`: the page needs JavaScript. Metas `robots noindex, nofollow, noarchive`, `referrer no-referrer`, `color-scheme`; **no Open Graph or Twitter tags** (the link only ever goes to the operator). Caddy: `handle /report-delete` → that file, `Cache-Control: no-store`; `/report-delete.html` stays `404`; ADR-032's site-wide headers and CSP apply unchanged | Smallest page that does it; no card to maintain for a link nobody pastes |
| DK-12 | **Invalid response, one:** `404`, JSON, `no-store`, byte-identical body `{"error":"not_found","message":"This delete link is no longer valid: it was already used, has expired, or the workout is gone."}` for unknown, malformed, absent, used, expired, gone, query string and Pushover off. Never `401`/`403`. Refusals are not logged (ADR-025 item 8). Lookup is by hash on a unique index; timing is not equalised (128-bit values, ADR-025 item 4's reasoning) | OQ-114; AC 35 |
| DK-13 | **Logging:** the key, its hash and both links never appear in a log line, error or response other than the Pushover request body. A redeem logs only `lifecycle`'s operator line. `pushover`'s failure lines stay as ADR-039 item 3 | AC 29, AC 32; TD Conventions (Logging) extended |
| DK-14 | **About (INF-1, OQ-119):** F-29 PT-9 becomes: Pushover receives the report number, the reason, the workout's viewing link and a single-use delete link, never the reporter's message; anyone with access to the operator's Pushover account or unlocked phone could use that link to delete the reported workout. App text in the template (AB-2), still rendered only when Pushover is on (AB-3, no Go change). The frontend engineer drafts it; the user owns the wording | AC 40 |

**Schema v5** (next free migration number, forward-only, no table rebuild; `TestSchema` pins it):

```sql
ALTER TABLE reports ADD COLUMN delete_key_hash BLOB CHECK (delete_key_hash IS NULL OR length(delete_key_hash) = 32);
CREATE UNIQUE INDEX reports_delete_key_hash ON reports (delete_key_hash) WHERE delete_key_hash IS NOT NULL;
```

## Verification focus (critical lane, QA effort high)

- Against the fake Pushover: the form fields of DK-10 only; a capped, dropped or failed-before-send report leaves `delete_key_hash` NULL; a byte scan of `workouts.db`, `-wal`, `-shm`, every log line and every response of a full open-and-confirm run finds no plain key.
- Single use under concurrency: parallel confirms of one key, one confirm per key of two reports on one workout, and a confirm racing the CLI delete: exactly one `204` and one operator log line.
- AC 32 reuses F-12's end-to-end list and F-21's byte scan after a phone delete while `serve` runs.
- DK-5: start with keys present and Pushover off; no hash remains.
- Phone (AC 41, user): lock-screen text shows no key; the anchor and `url` open the right pages in the Pushover app (OQ-125).
