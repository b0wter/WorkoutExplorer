# ADR-023 Identifying data stripped by a byte-level rewriter: history

This file holds, verbatim, what was moved out of it on 22 Oct 2026 (restructuring, no decision changed): the revision list of the header and every struck-through or replaced passage. ## Struck-through and replaced passages

Each item is the original text; the live document states the current form.

**Item 3, architecture byte:** architecture ~~(0 little-endian, 1 big-endian)~~ (rev. 7: **0 little-endian, every other value big-endian**, as the decoder reads it, `decoder.go:550-554`),

**Item 3a, first bullet:** - Where the decoder accepts something unusual, the strip mirrors it. ~~The strip may refuse (`errRecordCount`, item 8) only where `Parse` also refuses. Refusing a file that `Parse` accepts would break "`Parse` accepts ⇒ `Accept` accepts" (Consequences).~~ (rev. 8) Reading a byte differently from the decoder is a defect in every case. `errRecordCount` means exactly that and is always `internal`. The strip may refuse a file that `Parse` accepts only through a deliberate refusal of item 8a. Reading a byte differently can store an identifier, as the rev. 7 input stored a `user_profile`.

**Item 3a, third bullet:** - The rev. 7 audit found one divergence (the architecture byte, fixed above). It found one rule that is the same only through an identity: the file CRC of a 14-byte header. The decoder starts it after the header, and the strip computes it over the header and its correct CRC, which leaves the CRC state at 0. Every other row is the same rule.

**Item 4, rev. 1 invalid value (struck in rev. 6):**

   ~~**Invalid value:** per base type (`base_type & 0x1F`) … A field whose size is not a multiple of its base type's size is filled with 0xFF throughout. Every decoder then reads the field as absent.~~ (rev. 6: wrong. It used the **declared** base type, and the decoder does not.)

   **Invalid value (rev. 6, replaces the paragraph above).** The fill follows the type the pinned decoder reads the field as.

**Item 4, "The short field is filled, not refused" (rev. 8 wording):** - **The short field is filled, not refused.** It holds no byte of the upload, so I-8 holds. Refusing would add a case in which `Parse` accepts and `Accept` refuses, for a stored file that leaks nothing. (rev. 8: the user's rule now allows such refusals for crafted input, but only where no faithful stored form exists, item 8a. A short field has one, so it stays filled.) Rewriting the definition so the field reads as unknown would change a definition message, which items 3 and 6 keep unchanged (OQ-48 accepted frame changes only). With the pinned profile a short field can occur only in the five `uint32` fields of 148 and 151 (148/4, 148/5, 151/4, 151/8, 151/9), declared with 1 to 3 bytes. ~~, or in any non-z field declared with size 0~~ (rev. 7: wrong, a size-0 field is absent). Zeros are the fill because they are what the decoder pads with: the field reads as if it had no bytes.

**Item 4, "Why rev. 1's rule failed":** - **Why rev. 1's rule failed** with the pinned decoder: a `uint32z` field declared `uint8` (the fuzz input) got 0xFF and read as 255; a `uint32z` field declared `uint32` got 0xFFFFFFFF; a z-type field of 5 bytes got all 0xFF. Each reads as a valid value. The original bytes were overwritten in every case, so no upload value was stored.

**Item 4, `TestBlankFill` bullet:** - `TestBlankFill` (F-09 v1.7) checks every blank-table field against every valid declared base type, a range of declared sizes and both byte orders, reading the result with the library's decoder. (rev. 7) The byte orders are now the architecture bytes 0, 1, 0x30 and 0xFF, and every case also runs the cross-check of item 3b.

**Item 6, complete sequence, replaced sentence:** ~~(rev. 4) The framing must read exactly `records` records (item 2) up to the end of the data region; any other count fails closed (item 8).~~ (rev. 5, replaces rev. 4's sentence) **The first `records` records are written**, as for a truncated sequence.

**Item 6, truncated sequence, opening:** - **Truncated** sequence: (rev. 4, replaces "framed as far as they go") **the first `records` records are written, and nothing after them**:

**Item 6a, first consequence:** - Before rev. 4, the rewriter's own framing went on past a record that it could frame but the decoder rejected. QA's probe kept 600 records when the sharer was shown 60. That can no longer happen: the stored original never holds data the sharer was not shown.

**Item 8 (rev. 5 and rev. 8 wording):** 8. **Failure is closed.** A complete sequence that the framing cannot read, (rev. 4) a framed record count that differs from the walk's `records` (a complete sequence with another count, or a truncated one in which fewer than `records` records can be framed; its own sentinel error, `errRecordCount`, whose cause names the sequence's byte offset and the two counts), a reparse that is rejected, or a reference mismatch makes `Accept` return `*ingest.Error{Kind: internal}` with a cause starting `strip:`. (rev. 5) Every framing disagreement now has the one sentinel `errRecordCount`: fewer than `records` records can be framed, in either status, or a complete sequence's framing fails check (a) or (b) of item 6. Its cause names the sequence's offset and what disagreed. The separate "cannot frame a complete sequence" error is gone. Exception to "a rejected reparse": a reparse rejected for the time limit returns the upload's `limit`/`time` error, because a time limit depends on load and does not say the file is unreadable (ADR-018 rev. 4). The upload is refused with "This file could not be read." (ADR-018), and one ERROR log line is written. The unstripped upload is never stored, never written to `tmp/`, and never logged. (rev. 8) Exception: the deliberate refusals of item 8a are `unreadable` at WARN. Every other failure in this item stays `internal`, which now always means a defect on our side.

**Item 8a, the rule, first bullet:** - ~~Files from real devices are accepted whenever `Parse` accepts them. Every synthetic corpus file and every local real file must pass `Accept`. A refusal of a real upload, of any kind, is a bug.~~ (rev. 9, the user, 22 Oct 2026) **No file is promised acceptance**, from a real device or not: nobody can know in advance what errors a device writes. Upload stores what it can store faithfully and refuses the rest under this item.

**Consequences, `ant_rx`/`ant_tx` bullet and its sub-bullet:**
- (rev. 3) `ant_rx` and `ant_tx` carry a `timestamp`. A file that has them between records written with compressed timestamps could reparse to a different workout once they are gone; step 1.5 then refuses the upload as `internal` (item 8; rev. 8: as `unreadable`, U2 of item 8a). No synthetic corpus file other than `identifying-data.fit` has these messages; the first "Would choose differently if" point covers it if real uploads are refused for it.
  - (rev. 5) This is the one known case left in which `Parse` accepts and `Accept` refuses. The decoder takes a compressed header's time from the last `timestamp` it read in any message (`decoder.go:641-644`, `742-745`), so the case covers any removed message whose definition has field 253, message 29 included. ~~It is **OQ-54**, open with the user: (a) keep refusing (proposed for now), or (b) in exactly this case, keep the message as a shell with only its `timestamp` valid.~~ (rev. 8) **OQ-54 closed by the user (21 Oct 2026): (a), refused.** It is deliberate refusal U2 (item 8a), `unreadable`, no longer `internal`. `TestAcceptRemovedTimestamp` (F-09) pins it.

**Consequences, the acceptance-property bullet:**
- ~~(rev. 5) **"`Parse` accepts ⇒ `Accept` accepts"** is the property `FuzzAccept` and `TestAcceptDataSizeSweep` check.~~ (rev. 8: superseded by the user's acceptance rule, item 8a. `TestAcceptDataSizeSweep` still checks the strict form, because a miscounted data size is damage a real device can produce. `FuzzAccept` and `TestFramingSweep` check the rule of item 8a: accepted with a faithful stored file, or refused as U1 or U2, never `internal`.) Its known exceptions are OQ-54 and the load-dependent outcomes (`canceled`, a time limit). The other cases found in QA round 3 are closed: a data size that ends inside a record (item 6), a last record cut by the end of the upload in a sequence the walk counts complete (item 6 (b)), overlapping sequences (item 7), and a stored file longer than `MaxBytes` (item 7, ADR-017 rev. 6).

**Consequences, rev. 6 bullet, sub-bullets 1 and 3:**
  - A short field (item 4) reads as 0 with the pinned decoder. `checkStored` accepts 0 exactly there: a non-z, non-string blank-table field that ~~a definition read earlier in the same sequence~~ (rev. 7) **the data message's own definition, the one active for its local type,** declared shorter than its profile type (F-09 v1.7, v1.8).
  - The rev. 6 fuzz input is closed without an exception to "`Parse` accepts ⇒ `Accept` accepts" (rev. 8: the rule is now item 8a's; the input is accepted under it as well). A stored original written under rev. 5 with such a definition is rewritten the next time F-30 runs `Accept` on it.

**Consequences, the table-upgrade bullet, last sentence:** (Rev. 3: the rev. 1 rule, `serial_number`, `*_ant_id`, `ant_device_number`, missed `ant_channel_id.device_number`, `segment_id.device_id` and the tank `sensor` fields, QA-09-r1 Q1.)

**Consequences, library upgrades, second sub-bullet:**
  - A later library that **rejects more** would make `Accept` on a stored original stop earlier. (A widened strip table may still shorten an original by removing messages; that is not this case.) Regeneration would then shorten the workout and cut its original further, and those bytes cannot be restored (one-way). ~~Rule for F-30: … F-30 changes neither the files nor the row for that workout, logs a WARN and ends with a non-zero exit, so the deploy stops.~~ (rev. 5, OQ-53 decided by the user, 21 Oct 2026) **The app does not store workouts long term, and this one-way door is accepted.** F-30 keeps the shorter regenerated workout, original included, and a deploy is never stopped to protect stored workouts. A stored original that the new version refuses is deleted like an expired workout (F-30). (rev. 8, OQ-53 follow-up 1, user) It is deleted only when the file itself is rejected (`not_fit`, `unsupported_type`, `no_data`, `unreadable`, `limit` other than `time`, `internal`). On `canceled`, a time limit or a server-side error the workout is kept for the next run (F-09 v1.9, F-30 hand-off). F-30 may count such changes for the deploy report.

**Would choose differently if, first two points:**
- Uploads are refused in practice because of a reference mismatch: remove such messages together with their timestamp's effect (rewrite the following compressed-timestamp records) instead of failing. (rev. 5) That is OQ-54. Its proposed option (b) keeps a timestamp-only shell instead of rewriting later records, because rewriting a compressed header needs a new definition, which would change data messages and not only the frame. (rev. 8) OQ-54 is closed as "refuse" (U2). ~~A real upload refused as U2 is a bug under item 8a, and it reopens this point with the user.~~ (rev. 9) Real uploads refused as U2 in practice reopen this point with the user. They are not a broken requirement (item 8a, rev. 9).
- ~~(rev. 8) A real upload is refused for any reason (`unreadable` included): by the user's rule that is a bug. Find a faithful stored form for it, add the file's pattern to the synthetic corpus, and never narrow the acceptance to cover it.~~ (rev. 9) Real uploads are refused in practice (`unreadable` included) often enough to matter to the users: look for a faithful stored form, add the file's pattern to the synthetic corpus, and never relax the corpus strictness to cover it. That is an improvement, not a bug fix: no file is promised acceptance (item 8a).
